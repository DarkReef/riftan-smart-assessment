# Подтверждаемый урон OW — кандидат Smart Assessment 0.3.0

Задача реализована в **Smart Assessment**, по явному запросу пользователя. Отдельного
модуля `riftan-combat-automation` не создаётся. UI не импортирует приватные файлы системы
и не зависит от Item Piles. F1-справочник, инвентарь и переводы компендиумов не менялись.

## Установка кандидата

1. Подготовьте копию тестового мира Foundry VTT 14.
2. Примените **отдельный патч ядра** к Apex Heresy RU base `32b1ef8` через `git am`.
   Система получит версию кандидата 1.5.6 и `game.darkHeresy.api.damage.version === 1`.
3. Распакуйте `riftan-smart-assessment.zip` в `Data/modules/riftan-smart-assessment`.
   В корне этой папки должны быть `module.json`, `scripts`, `templates` и CSS.
4. Включите Smart Assessment 0.3.0, войдите активным GM и игроком.
5. Публичные latest URL ещё относятся к опубликованным версиям: этот кандидат не
   выпущен, тег не опубликован. Установка выполняется из приложенного ZIP.

Base модуля: локальный commit `53e7dc5` (подготовленная ранее F1-справка 0.2.0).
Он не был опубликован. Патч этой задачи накладывается поверх него; полный ZIP и
архив исходников самостоятельны и содержат всё необходимое. Патч ядра и модульный
пакет поставляются отдельно, модуль в системный ZIP не добавляется.

## Пользовательский путь

В новой штатной карточке урона нажмите **«Запросить расчёт GM»**. Цель берётся из
записанных targets; при нескольких выбирается ровно одна. Текущее выделение и
назначенный пользователю персонаж не заменяют её. Если цели не было в броске,
интерфейс сообщает об этом; для GM есть отдельный программный путь с targetReason.

GM нажимает **«Рассчитать»** в запросе или исходной карточке. Подробности раскрываются
в этой карточке. Неразрешённая реакция даёт **«Ожидает защиты»**. Через **«Изменить»**
GM записывает причину отсутствия/разрешения реакции, решение по полю и критам/RF,
при необходимости — итог каждого попадания и известные состояния с длительностью.
Только редактирование решения открывает отдельное окно; лист цели не требуется.

Кнопка **«Проверить поле»** — отдельное явное разрешение бросков поля. Обычный preview
не бросает кости и не меняет документы. Для очереди GM должен явно принять политику
«по каждому попаданию» и записать причину. Поддержано отражающее поле;
другие поля с побочными эффектами и особыми исключениями требуют ручного решения.

От готового разрешённого preview до применения — одно нажатие **«Применить»**.
В GM-карточке: «Осталось ран: 3 → −3», разбивка по каждому попаданию, обычные и
критические повреждения, отдельный RF. Игрок получает разрешённый статус без
секретных AP/БВ/остатка ран NPC. Повторный рендер не выполняет механику.

**Ручной итог** — количество повреждений после **всех** защит и True Grit. При его
использовании True Grit повторно не вычитается. Исходный штатный расчёт остаётся
предварительной разбивкой, причина GM и реальный итог сохраняются в квитанции.
Нельзя задавать ручной итог без причины или пропускать значения отдельных попаданий.

## Договор с системой

Требуется Apex Heresy 1.5.6 с публичным damage API **v1**:
`request`, `preview`, `resolveField`, `commit`, `getReceipt`.
Система отвечает за Only War арифметику, валидацию, активного GM и сохранение.
Модуль отвечает за UI. Штатный `api.applyDamage({messageId})` совместим: в режиме
подтверждения OW создаёт запрос. Иные rulesets продолжают штатные пути.

Снимок содержит сохранённые кости, СУ, локации, профиль оружия/боеприпаса и hit IDs.
Модификации повторно не накладываются. Уже рассчитанные повреждения и расход патронов
не перебрасываются/не повторяются из-за подтверждения. Старые карточки без метаданных
качества оружия требуют needs-review и явного ручного итога.

Wounds и минимальный маркер операции меняются одним Actor.update. Перегрузка поля и
состояния — последовательные дополнительные документы с журналом намерения/результата.
Локальная очередь не является распределённой блокировкой. После сетевого сбоя,
потери роли или смены GM операция не воспроизводится вслепую.

GM-квитанции зашифрованы AES-GCM в flags, а не просто скрыты whisper/CSS. Ключ
клиентский, в документах отсутствует. Подробности квитанции доступны на браузере
GM, который её сохранил. При потере ключа/смене браузера требуется ручная проверка;
переноса ключей и автоматического восстановления в v0.1 нет. Это относится к новым
журналам; старые карточки сторонних модулей этот пакет ретроактивно не переписывает.

## Реализованное и явные границы

Реализованы: обычные OW персонажи/NPC, synthetic/linked Actor, одна закреплённая цель,
попадания очереди по своим зонам, Pen, +X/дополнительные успешные СУ, Felling,
True Grit, обычные/критические счётчики и отдельный RF; проверки stale/Fate/прав;
сохранённые решения GM и повторозащищённые выбранные штатные состояния.

Неподдерживаемая автоматизация: критические таблицы целиком, универсальный порог
смерти, полные on-hit эффекты Toxic/Flame/Shock/Corrosive/Concussive/Snare и др.,
психосилы, Blast/AoE, техника, орды, корабли, массовые цели, двойное оружие и несколько
независимых карточек урона одной атаки, другие rulesets, полный Undo.
Daemonic и Warp Weapon не подменяются Pen/Felling: неизвестные исключения и
взаимодействия требуют needs-review. Разрешён явно ручной итог; предварительная
разбивка не выдаётся за полностью проверенную автоматизацию.

Две независимые записи нескольких документов не называются атомарной транзакцией.
Не обещается автоматический откат всех последствий. При частичной записи квитанция
сохраняет stage, intent, доступные результаты и woundsRecorded; повтор запрещён.

## Автоматическая проверка

```text
В ядре: npm test
В модуле: npm test
В модуле: npm run test:e2e
```

Для E2E задайте `APEX_SYSTEM_DIR` как каталог ядра с применённым патчем, установите
Playwright/Chrome или задайте `PLAYWRIGHT_MODULE` и `BROWSER_CHANNEL`.
`QA_OUTPUT_DIR` задаёт каталог скриншотов (по умолчанию dist). E2E запускает локальный
host на 127.0.0.1:18764, использует настоящие новый API/методы Actor и UI, три отдельные
браузерные сессии с ролями GM/owner/non-owner. Персистентность и сетевой host
моделируются в памяти. Пользовательский мир не открывается и не изменяется.

Сквозные фиксированные проверки в ядре охватывают таблицу Pen/Felling из ТЗ,
True Grit 3 обычных + 3 критических (remaining −3), отдельные локации, 0 поглощённого
урона, RF отдельно, +X/провал, реальные изменения характеристики, linked/unlinked,
Fate replacement, повторные вызовы, no-GM/lost permission, stale, ошибки до/после
записи, ciphertext и другой ключ GM. Старый тест порядка строк поля заменён
проверкой поведения: два штатных запроса → один бросок поля, ноль ран при блоке.

## Живой Foundry — воспроизводимая приёмка

**Живой multiplayer QA не выполнен.** Manifest verified не доказывает эту проверку.
До эксплуатации проведите следующий сценарий на копии мира:

1. GM + два игрока; у первого OW Actor-владелец, у второго нет прав на него/врага.
2. Два unlinked токена одного NPC и два linked токена общего Actor. Запрос на один
   unlinked меняет только его synthetic Actor; linked работают на общий Actor.
3. NPC: T=45, +X=3, AP=6, raw=18. Проверьте пять строк Pen/Felling из исходного ТЗ.
4. True Grit, max=12/value=9/critical=0, Pen4/Felling2: value12/critical3, осталось−3.
5. Реальное AE характеристики +10 и отдельный модификатор теста: только первое
   меняет БВ. AE/Item/поле одного +X не складываются повторно и не запекаются в source.
6. Штатные Dodge/Parry с привязкой к той же цели; без привязки pending-defense.
7. Отражающее поле, очередь минимум 3 попадания, явная политика per-hit; успех поля
   не отменяет всю очередь, перегрузка и результаты не повторяются при reload/click.
8. Крит/RF: GM читает точную таблицу и назначает известное состояние один раз.
9. Двойной клик, второй запрос, native apply, повтор после refresh. Расход патронов
   и кости не повторяются. Другой клиент/GM без ключа не воспроизводит старую операцию.
10. Между preview/commit измените AP, T, раны или эффект: stale, нужна новая проверка.
11. Fate-reroll до применения инвалидирует старую карточку; после применения не
    переписывает квитанцию/раны. Смена GM/потеря прав/отключение сети → видимый отказ.
12. Открытый и закрытый бросок: второй игрок не видит подробные значения NPC ни в
    новом content, ни в plaintext flags; публично только разрешённый статус.
13. Отключите модуль; проверьте штатный бой, Charbar, AE/Fate и остальные rulesets.
